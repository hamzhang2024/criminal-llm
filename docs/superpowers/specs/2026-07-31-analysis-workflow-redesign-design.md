# 案卷分析工作流重构设计文档

> 日期：2026-07-31
> 状态：待用户批准
> 范围：criminal-llm（backend 分析流水线 + 证据提取 + 前端）
> 前置：案例检索服务已上线（见 2026-07-29-case-retrieval-design.md）

## 1. 背景与目标

当前分析流水线（analysis_pipeline.py）存在四个方法论缺陷：

1. 法律依据检索（4c）在证据摄入（4b）**之后**，证据审查缺少法律框架指引
2. 辩护思路由 LLM 全程自动生成，**律师在"定方向"环节缺位**
3. 类案裁判规则（案例检索服务已具备）未进入分析主流程
4. 证据提取只按"罪名"指引，粒度粗；长文直接截断丢失内容；完整性无校验；封面/目录等非证据页无标注

目标：重构为"法律框架先行 + 律师掌舵 + 完整性可核验"的分析工作流。

### 已确认的决策（用户拍板）

| 决策点 | 结论 |
|---|---|
| 法律框架位置 | 4c 前移到 4a 之后，并扩展为"法条 + 司法解释 + 类案裁判规则" |
| 类案结合方式 | 自动检索只作分析参考；报告正式引用仍走手动勾选（可核验性底线） |
| 辩护思路 | 新增 4.75 确认卡点：系统生成建议 → 用户勾选/修改/补充 → 确认后驱动步骤 5 |
| 长文处理 | 分块提取 + 合并去重（map-reduce），不丢内容 |
| 完整性校验 | 规则对账（编号项核对）+ LLM 抽检起诉书类关键文书 |
| 上下文适配 | 统一预算模块覆盖提取与分析两侧：窗口映射 + 优先级截断 + 整体性分析摘要压缩，替代硬截断 |
| 非证据页 | 封面/目录/封底/备考表**标注为非证据但保留**，不删除（案卷完整性） |

## 2. 重构后的完整流程

```
预处理（CaseDetailPage）
  步骤0 上传 PDF → 步骤1 去水印 → 步骤2 PDF转MD
  步骤3 证据提取【改动 C/D/E】
    ├─ 前置：罪名 → 一次性轻量检索法律框架（要件+法条+类案），缓存
    ├─ 文书分类：证据 / 非证据（封面/目录/封底/备考表），非证据保留不入提取
    ├─ 提取 prompt 注入法律框架固定前缀（提升缓存命中率）
    ├─ 长文分块提取 → 合并去重
    ├─ 证据标注：关联罪名 + 关联要件（新增 elements 字段）
    └─ 完整性校验：规则对账 + LLM 抽检 → 完整性报告

分析流水线（analysis_pipeline.py）
  步骤1 合并笔录 → 步骤2 逐次详细总结 → 步骤3 内部矛盾分析【改动 F：边界厘清】
  步骤4 案件 Wiki
    4a 指控要素分析
    4c 法律框架构建【改动 A：前移+扩展】
       ├─ 法条 + 司法解释（现有）
       └─ 类案裁判规则 top 3（自动检索，标注"供分析参考"）
    4b 逐人证据摄入（带法律框架+证据要件标签）
    4d 综合结论
  步骤4.5 控辩对抗
  步骤4.75 辩护思路确认【改动 B：新增卡点】
    ├─ 系统生成《辩护思路建议》（主攻/备选/依据/风险）
    ├─ 流水线进入"待确认"状态，前端弹出确认面板
    ├─ 用户：勾选/修改/删除建议 + 自由补充（律师思路优先）
    └─ 确认稿存 analysis/04.75-辩护思路/思路确认.md
  步骤5 辩护意见六节（prompt 注入已确认辩护思路）
```

## 3. 改动 A：4c 前移 + 类案裁判规则

**顺序**：`4a → 4c → 4b → 4d`（原 `4a → 4b → 4c → 4d`）

**4c 扩展**：
- 现有：`search_and_merge(crime_type)` 法条检索，存 Wiki `04-法律依据/`
- 新增：按罪名调 `GET /api/case-search/search?charge=<罪名>&size=3` 取 top 3 卡片（罪名精确过滤），取 `holding_summary` + `reasoning_excerpt`，存 Wiki `04-法律依据/类案裁判规则-<罪名>.md`，开头标注"以下为自动检索的类案裁判规则，供分析参考，正式引用需人工确认"
- 降级：无 API Key / 检索失败 / 0 结果 → 静默跳过，法条路径照常
- 配额：每次分析每罪名 1 次检索，进度提示"已检索类案 N 篇"

**4b/4d prompt**：加入法律框架上下文（要件 + 法条 + 裁判规则），4b 评估证据时关联"证据 ↔ 要件 ↔ 裁判规则"

**断点续传适配**：子步骤标记 4b/4c 的完成状态按新顺序处理；旧案件的既有标记不迁移（重跑即可，文档说明）

**步骤 5**：`04-三阶层辩护` prompt 从 Wiki `04-法律依据/` 读取时自然获得类案裁判规则（无需额外改动）

## 4. 改动 B：4.75 辩护思路确认卡点

### 4.1 系统建议生成

`step475_defense_strategy(defendant, crime_type)`：
- 输入：Wiki 综合结论（06）+ 矛盾记录（05）+ 控辩对抗结果（04.5 法官裁决）
- 输出《辩护思路建议》MD：主攻方向（1-2 个）/ 备选方向 / 每方向的依据（引用具体证据编号与裁判规则）/ 风险点
- 存 `analysis/04.75-辩护思路/系统建议.md`

### 4.2 待确认状态机

- `analysis_state.json` 新增状态：`awaiting_strategy_confirmation`
- 流水线跑到 4.75 生成建议后置该状态并返回；`GET /api/pipeline/{case_id}/analysis-state` 透出
- 新端点：
  - `GET /api/pipeline/{case_id}/defense-strategy` → 系统建议 + 当前确认稿（如有）
  - `POST /api/pipeline/{case_id}/defense-strategy/confirm` body `{selected: [...], edited: {...}, user_additions: [...]}` → 写 `思路确认.md`（含原始建议 + 用户改动痕迹）→ 清除待确认状态 → 继续步骤 5
  - `POST .../defense-strategy/confirm` 支持 `{"use_system_default": true}` 一键采纳

### 4.3 步骤 5 prompt 注入

六节每节 prompt 头部加：
```
辩护思路（律师已确认，必须遵循；律师补充的思路优先级最高，与系统建议冲突时以律师为准）：
{思路确认.md 内容}
```

### 4.4 前端确认面板

CaseDetailPage 分析进度轮询到 `awaiting_strategy_confirmation` 时弹出面板：
- 系统建议列表（每条：方向 + 依据 + 风险，可勾选/编辑文本/删除）
- 自由补充框（多条添加）
- [确认并继续] / [直接采用系统建议]
- ReportPage 报告增加"辩护思路"小节展示确认稿

## 5. 改动 C：证据提取注入法律框架指引

**前置轻量检索**（每案件每罪名一次，缓存到 `evidence/legal_framework.json`）：
- 构成要件拆解（LLM，基于内置 legal_knowledge）
- 类案裁判规则 top 2（案例库检索，无 Key 降级跳过）
- 失败降级：退化为现有"仅罪名"模式

**提取 prompt**：法律框架作为固定前缀（符合现有 prompt cache 优化：固定前缀在前、文件内容在后）

**证据标注**：`index.json` 每条证据新增 `elements: [...]`（关联要件，如"轻微暴力""主观明知"）；旧案件无此字段照常工作

## 6. 改动 D：统一上下文预算管理（提取 + 分析）+ 长文分块

### 6.1 统一预算模块 `backend/context_budget.py`

- **窗口识别**：模型名 → 上下文窗口映射表（deepseek 系 128K、qwen 系 131K、kimi 系 256K、1M 系列等，未知用配置值）；保留 `model_context_limit` 配置（默认 250000）作为用户覆盖项；设置页改模型时自动建议，用户可改
- **换算**：1 token ≈ 1.5 中文字；`char_budget(ratio)` 统一换算
- **预算分配**：system prompt + 输出预留 20%，剩余为内容预算
- **核心工具 `fit_texts(texts, budget)`**：输入 `[(标签, 文本, 优先级)]`，按优先级分配预算——高优先级（起诉书/起诉意见书）完整保留，中优先级（笔录/关键证据）比例分配，低优先级（次要材料）截断并标注 `[已截断，原文 X 字]`；替代现有 `[:40000]`/`[:50000]` 硬截断

### 6.2 提取侧：长文分块（map-reduce）

- 文件 ≤ 预算：现有单次提取
- 文件 > 预算：按**段落边界**切块（不切断段落，每块 ≤ 预算 × 0.9，块间重叠 500 字防跨块事实被切断）→ 每块独立提取（并发受现有信号量控制）→ 合并：按"事实描述 + 时间 + 人物"去重，证据编号在合并后统一重排
- 每块提取的输出 schema 与现有完全一致，合并逻辑纯规则（不再调 LLM）
- 断点续传：块级进度记录（已完成的块跳过）

### 6.3 分析侧：按阶段策略

| 场景 | 策略 |
|---|---|
| 证据清单类注入（步骤 5 各节、stage_4/5 的 evidence_context） | `fit_texts` 优先级截断 + 截断标注（替换现有 `[:40000]` 硬截断） |
| 整体性分析（4d 综合结论、步骤 2 多人总结汇总） | 超预算时先对**低优先级部分**做一次 LLM 摘要压缩（map-reduce-lite：逐块摘要 → 摘要合并注入），高优先级原文保留 |
| 步骤 2 逐次总结 | 单次笔录通常不超预算；超预算走 6.2 同款分块 |
| 4.75 思路生成 / 4.5 控辩对抗 | 输入以 Wiki 摘要为主，`fit_texts` 即可 |

- 所有注入点在日志打印 `预算使用: X/Y 字符 (Z%)`，便于调优
- 小模型（≤128K）下自动收紧：证据标注摘要长度、类案卡片 top 3 → top 2

## 7. 改动 E：完整性校验 + 非证据标注

### 7.1 文书分类（提取前）

`classify_document(filename, first_500_chars) -> "evidence" | "non_evidence:<subtype>"`：
- 规则优先：文件名含 封面/目录/封底/备考表/卷内目录 → 非证据对应子类
- 规则不中：LLM 轻量判定（只看开头 500 字，一次调用）
- `index.json` 文件级新增 `doc_type` 字段；非证据文件**保留在原目录和文件列表**，不入提取流程，UI 显示灰色"非证据"徽标，4b 摄入跳过

### 7.2 完整性校验（提取后）

**规则对账**（全文件，零 LLM 成本）：
- 从原文提取编号项模式：`第X笔/第X起`、中文序号`一、二、三`、阿拉伯`1. 2. 3.`
- 与提取清单的事实条目逐条比对（标题关键词重合度），输出每个文件：原文编号数 / 提取数 / 疑似遗漏条目

**LLM 抽检**（仅起诉书/起诉意见书/判决书）：
- "原文列出 N 笔事实，提取清单是否逐笔覆盖？输出遗漏清单"
- 一次调用/文书

**完整性报告**：存 `evidence/completeness_report.json` + 前端 CaseDetailPage 证据列表顶部展示（每文件绿/黄/红状态点），疑似遗漏支持"针对该文件重提"

## 8. 改动 F：矛盾分析边界厘清（纯 prompt）

- 步骤 3：仅"供述内矛盾"（同一人前后说法不一）
- 4b 矛盾记录：仅"证据间矛盾"（不同证据/不同人互相冲突）
- 两个 prompt 各加一句边界声明，不动代码结构

## 9. 界面改动（让新顺序可感知）

### 9.1 CaseDetailPage（流水线工作流）

- 分析阶段的步骤展示更新为新顺序：指控要素 → 法律框架（含类案）→ 证据摄入 → 综合结论 → 控辩对抗 → **辩护思路确认** → 辩护意见
- 辩护思路确认：轮询到 `awaiting_strategy_confirmation` 时，步骤指示器高亮"待确认"并弹出确认面板（见 4.4）
- 证据提取阶段：文件列表显示非证据徽标（灰色"非证据"）与完整性状态点（绿=完整 / 黄=疑似遗漏 / 红=校验失败），顶部显示完整性摘要（"12 份证据完整，1 份疑似遗漏"）

### 9.2 ReportPage（报告页）

- **标签顺序调整**（反映新流水线顺序）：
  指控要素 → 人物关系 → 事件拆解 → 法律法规 → 证据列表 → 矛盾分析 → 控辩对抗 → **辩护思路（新增）** → 三阶层分析 → 完整报告
- **辩护思路 tab**：展示确认稿（系统建议 + 律师补充 + 修改痕迹），只读 + "重新编辑"入口（回到确认面板，改后重跑步骤 5）
- **法律法规 tab**：Wiki `04-法律依据/` 下类案裁判规则文件渲染为独立小节（标注"自动检索，供参考"）；案例库检索面板（已有）位置不变
- **证据列表 tab**：非证据徽标 + 完整性状态点（同 9.1）

### 9.3 设置页

- 模型上下文窗口：改模型时显示自动识别的窗口大小（可覆盖）

## 10. 错误处理与降级

| 场景 | 行为 |
|---|---|
| 无案例 API Key | 类案检索全链路静默跳过，法条路径照常（改动 A/C 一致） |
| 分块中单块失败 | 该块按现有重试策略；最终仍失败的块记入完整性报告"未提取块"，不阻塞整文件其他块 |
| 4.75 用户长期不确认 | 流水线保持待确认状态（断点续传），无超时；前端每次进入案件都提示 |
| 思路确认为空（全删光） | 视为"use_system_default"，步骤 5 照常 |
| LLM 抽检与规则对账冲突 | 报告同时呈现两者，以 LLM 抽检为准标注"建议人工复核" |

## 11. 测试策略

- 上下文预算：窗口映射表命中/回退、fit_texts 优先级分配（高优先级不被截断）、摘要压缩仅在超预算时触发
- 分块/合并：构造超预算文件（mock LLM），验证块边界不切断段落、重叠区事实去重、编号重排、断点续块
- 完整性规则对账：多模式编号 fixture
- 文书分类：规则命中/LLM 兜底/误判为证据的兜底（宁可误提取不误标非证据——非证据判定需高置信，拿不准归证据）
- 4.75：状态机流转（生成建议→待确认→确认→步骤 5 拿到注入）、一键默认、空确认
- 4c 前移：Wiki 目录顺序、类案降级路径
- 前端：确认面板交互（Playwright）

## 13. 明确不做（YAGNI）

- 两套分析系统（stage_api / pipeline）合并——长期方向，本期不动
- 类案自动检索结果直接进报告引用——保持手动确认底线
- 非证据文件的自动清理——明确保留，永不删除
- 多模型自动切换/路由——只做上下文窗口映射与预算适配
